## Access Token Claims {#access-token-claims}

A `DataAddress` generated by a [=Data Plane=] may carry an access token that the requesting party presents to the
API exposed at `endpoint`. Transfer Profiles such as the [HTTP Transfer Profile](#http-transfer-profile) and the
[Token Renewal](#token-renewal) profile deliberately do not mandate the format of that token: it is opaque to the
requesting party, and its structure is a private matter between the party that issues it and the application that
validates it.

In many deployments, however, the application behind `endpoint` is not the [=Data Plane=] itself but a separate
service that only receives the token. Such an application benefits from a predictable set of claims that it can use
to authorize a data request without calling back into the [=Data Plane=]. This profile defines that claim set.

The claim set is an **information model** and is independent of any token encoding. Its claim names are taken from
the [IANA JSON Web Token Claims registry](https://www.iana.org/assignments/jwt/jwt.xhtml), so that the same names
apply unchanged whether the token is a JWT ([RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519)), a CWT
([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)), or an opaque string whose claims are exposed through
token introspection ([RFC 7662](https://datatracker.ietf.org/doc/html/rfc7662)). The
[Format Bindings](#access-token-claims-format-bindings) section defines how the claim set is encoded for each of
these cases.

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “NOT
RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in
[RFC 8174](https://datatracker.ietf.org/doc/html/rfc8174).

### Scope and Conformance

> This section is normative.

This profile uses the following roles:

- The **issuing party** is the [=Data Plane=] that generates the `DataAddress` containing the access token, or an
  authorization server acting on its behalf. For a pull transfer this is the provider [=Data Plane=]; for a push
  transfer it is the consumer [=Data Plane=].
- The **requesting party** is the party that presents the access token to the API exposed at `endpoint`.
- The **receiving application** is the service behind `endpoint` that validates the access token and authorizes the
  data request. It MAY be the issuing party itself or a separate service.

Support for this profile is OPTIONAL. A Transfer Profile that carries an access token in its `DataAddress` MAY
reference this profile; it MUST NOT require the requesting party to understand the token.

The following requirements apply:

- The requesting party MUST treat the access token as an opaque string. It MUST NOT rely on the token having any
  particular format or containing any particular claim.
- An issuing party that supports this profile MUST include every claim marked MUST in the
  [Claim Set](#access-token-claims-claim-set), and MAY include any other claim.
- A receiving application MUST verify that the token has not expired (`exp`) and that it is the intended audience
  (`aud`) before authorizing a request.
- A receiving application MUST ignore claims it does not understand.
- A receiving application MUST reject a token whose encoding it cannot verify.

### Claim Set {#access-token-claims-claim-set}

> This section is normative.

An access token conforming to this profile conveys the following claims:

| Claim         | Requirement | Description                                                                                                                                                                                                                                                       |
|---------------|-------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `iss`         | MUST        | Identifier of the issuing party's token issuer.                                                                                                                                                                                                                   |
| `sub`         | MUST        | The participant identity of the requesting party. This MUST equal the `counterPartyId` of the `DataFlowPrepareMessage` or `DataFlowStartMessage` that initiated the data flow. When DCP identities are used, this is the requesting party's DID.                  |
| `aud`         | MUST        | Identifier of the receiving application, typically the `endpoint` of the `DataAddress` or the identifier of the issuing [=Data Plane=]. A receiving application MUST reject a token whose `aud` does not name it.                                                 |
| `iat`         | MUST        | The time at which the token was issued (seconds since Unix epoch).                                                                                                                                                                                                |
| `exp`         | MUST        | The expiration time of the token (seconds since Unix epoch). Receiving applications MUST reject expired tokens. When the [Token Renewal](#token-renewal) profile is used, `exp` MUST be consistent with the `expiresIn` property of the `DataAddress`.            |
| `jti`         | SHOULD      | A unique token identifier. Receiving applications MAY use this for auditing and for revoking an individual token.                                                                                                                                                     |
| `dataFlowId`  | MUST        | The identifier of the [=Data Flow=] the token grants access to. This MUST equal the `dataFlowId` of the `DataFlowPrepareMessage` or `DataFlowStartMessage`, which in turn equals the transfer process identifier assigned by the [=Control Plane=].              |
| `datasetId`   | SHOULD      | The identifier of the [=Dataset=] being transferred. This MUST equal the `datasetId` of the `DataFlowPrepareMessage` or `DataFlowStartMessage`.                                                                                                                  |
| `agreementId` | SHOULD      | The identifier of the contract agreement under which the data flow takes place. This MUST equal the `agreementId` of the `DataFlowPrepareMessage` or `DataFlowStartMessage`.                                                                                     |

The claims `dataFlowId`, `datasetId` and `agreementId` are private claim names in the sense of
[RFC 7519, Section 4.3](https://datatracker.ietf.org/doc/html/rfc7519#section-4.3). Their names are chosen to match
the corresponding properties of the Data Plane Signaling messages so that a receiving application can correlate a
token with a data flow without translation.

### Propagated Counterparty Claims {#access-token-claims-propagated}

> This section is normative.

The `DataFlowPrepareMessage` and `DataFlowStartMessage` carry a `claims` object containing the Dataspace Protocol
claims of the counterparty as verified by the [=Control Plane=]. An issuing party MAY propagate entries of that
object into the access token so that the receiving application can base authorization decisions on them.

When propagating counterparty claims, the following rules apply:

- A propagated entry MUST carry the same name and the same value as the corresponding entry of the `claims` object.
  The issuing party MUST NOT add, alter, or derive claims that the [=Control Plane=] did not verify.
- A propagated entry MUST NOT use a name defined in the [Claim Set](#access-token-claims-claim-set). If an entry of
  the `claims` object collides with one of those names, the issuing party MUST NOT propagate it.
- Which entries are propagated is a policy decision of the issuing party. This profile does not enumerate them.
  Issuing parties SHOULD propagate only the entries a receiving application needs for authorization.
- A receiving application MUST NOT treat a propagated claim as verified unless it trusts the token issuer (`iss`) to
  have obtained that claim from a [=Control Plane=]. This profile defines no mechanism for a receiving application to
  verify propagated claims against the [=Control Plane=].

The following is a NON-NORMATIVE example of a `claims` object as carried in a `DataFlowStartMessage`:

```json
{
  "claims": {
    "membership": {
      "issuer": "did:web:dataspace-authority.example.com",
      "level": "gold"
    },
    "region": "EU"
  }
}
```

The following is a NON-NORMATIVE example of the corresponding claim set in which the issuing party has chosen to
propagate the `region` entry only:

```json
{
  "iss": "https://provider.example.com",
  "sub": "did:web:consumer.example.com",
  "aud": "https://provider.example.com/data/asset-123",
  "iat": 1750000000,
  "exp": 1750000300,
  "jti": "f3b2c4d0-9a1e-4c2f-8e4d-1a2b3c4d5e6f",
  "dataFlowId": "test-transfer-process-id",
  "datasetId": "asset-123",
  "agreementId": "test-agreement-id",
  "region": "EU"
}
```

### Format Bindings {#access-token-claims-format-bindings}

> This section is normative.

A format binding defines how the [Claim Set](#access-token-claims-claim-set) is encoded in a concrete token
representation. An issuing party MAY use any binding defined in this section. The choice of binding is invisible to
the requesting party and MUST NOT be signalled in the `DataAddress`.

#### JWT Binding {#access-token-claims-jwt}

When the access token is a JSON Web Token, it MUST conform to the JWT Profile for OAuth 2.0 Access Tokens defined in
[RFC 9068](https://datatracker.ietf.org/doc/html/rfc9068). In particular:

- The JWT MUST be signed as a JWS ([RFC 7515](https://datatracker.ietf.org/doc/html/rfc7515)). Unsecured JWTs
  (`alg` of `none`) MUST NOT be used.
- Each claim of the [Claim Set](#access-token-claims-claim-set) is encoded as a JWT claim of the same name, with the
  value types defined by [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519). `aud` MAY be a single string or
  an array of strings.
- A receiving application MUST validate the token as described in
  [RFC 9068, Section 4](https://datatracker.ietf.org/doc/html/rfc9068#section-4).

How the receiving application obtains the key material used to verify the signature is out of scope for this
profile. Issuing parties MAY publish a JSON Web Key Set ([RFC 7517](https://datatracker.ietf.org/doc/html/rfc7517))
for this purpose.

#### Opaque Token Binding {#access-token-claims-introspection}

When the access token is an opaque string, the issuing party MAY expose the [Claim Set](#access-token-claims-claim-set)
through an OAuth 2.0 Token Introspection endpoint as defined in
[RFC 7662](https://datatracker.ietf.org/doc/html/rfc7662). In that case:

- The introspection response for an active token MUST contain `active` set to `true` and MUST contain each claim of
  the [Claim Set](#access-token-claims-claim-set) marked MUST as a top-level member of the same name. Other claims
  MAY be included under their own names.
- The introspection response for an unknown, expired, or revoked token MUST contain `active` set to `false` and
  SHOULD contain no other members.
- The location of the introspection endpoint and the means by which the receiving application authenticates to it
  are deployment-specific and out of scope for this profile.

The following is a NON-NORMATIVE example of an introspection response:

```json
{
  "active": true,
  "iss": "https://provider.example.com",
  "sub": "did:web:consumer.example.com",
  "aud": "https://provider.example.com/data/asset-123",
  "iat": 1750000000,
  "exp": 1750000300,
  "jti": "f3b2c4d0-9a1e-4c2f-8e4d-1a2b3c4d5e6f",
  "dataFlowId": "test-transfer-process-id",
  "datasetId": "asset-123",
  "agreementId": "test-agreement-id"
}
```

#### Other Encodings

The claim names used by this profile are registered for both JWT and CBOR Web Token (CWT,
[RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)) through the IANA registries. A CWT binding is not defined
by this profile; an issuing party that uses CWT SHOULD apply the [JWT Binding](#access-token-claims-jwt) by analogy,
using the CWT claim keys registered for the same names.

### Relationship to Token Renewal {#access-token-claims-token-renewal}

> This section is normative.

When the [Token Renewal](#token-renewal) profile is used together with this profile, an access token issued in
response to a refresh request MUST carry the same [Claim Set](#access-token-claims-claim-set) as the token it
replaces. The `sub`, `dataFlowId`, `datasetId` and `agreementId` claims MUST be unchanged. The `iat`, `exp` and
`jti` claims MUST reflect the newly issued token.

### JSON Schema

> This section is normative.

The JSON Schema for the [Claim Set](#access-token-claims-claim-set) is published at:

```
https://w3id.org/dspace-sig/profile/access-token-claims/claims-schema.json
```

The schema describes the claim set as a JSON object, which corresponds to the payload of a JWT under the
[JWT Binding](#access-token-claims-jwt) and to the introspection response, minus the `active` member, under the
[Opaque Token Binding](#access-token-claims-introspection). The schema permits additional members so that propagated
counterparty claims and claims unknown to this profile validate.
